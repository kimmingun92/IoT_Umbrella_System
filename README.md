# 다중 보드 프로토콜-DB 연동 IoT 우산 보관 시스템

장마철 공공장소 우산꽂이에서 발생하는 도난·분실 문제를 해결하기 위한 프로젝트. RFID 카드로 본인 우산을 슬롯에 자동 등록하고, 등록된 카드로만 회수가 가능하도록 해 도난·분실을 방지한다. 젖은 우산은 자동 건조 기능으로 방치 문제도 함께 해결하고, 관리자는 전체 슬롯 현황을 통합 모니터링할 수 있다.

Arduino(현장 제어) · Raspberry Pi(멀티스레드 TCP 서버 + DB) · STM32(관리실 표시부) 3개 이기종 보드가 서로 다른 통신 경로(TCP/Bluetooth/UART)로 연동되며, 모든 이벤트가 MySQL에 트랜잭션 단위로 기록된다.

**기간**: 2026년 5월 28일 → 2026년 6월 4일

## 핵심 포인트
- RFID 기반 개인 인증(접근 제어) + IR 센서 기반 강제 인출(도난) 감지
- 아두이노·라즈베리파이·STM32 간 통신 프로토콜을 직접 설계 (TCP/Bluetooth/UART, 메시지 라우팅 규격 자체 정의)
- 라즈베리파이에 pthread 기반 멀티스레드 TCP 서버를 구현해 여러 종류의 클라이언트(아두이노/DB클라이언트/블루투스클라이언트)를 동시 수용
- MySQL로 user/slot/log 3테이블을 설계, 보관·회수·건조·도난 4개 이벤트를 트랜잭션 기반으로 기록
- 멀티스레드 환경에서의 공유 자원 경쟁(레이스 컨디션), 센서 노이즈로 인한 상태 채터링 등 실제 동작 중 발생한 문제를 진단하고 구조적으로 해결

## 시스템 아키텍처

| 구성 요소 | 위치 | 역할 |
|---|---|---|
| Arduino | 우산꽂이 (외부) | 현장 제어부 — RFID 인식, 서보모터 잠금/해제, IR센서, 수위센서, DC모터, 부저·LED 제어. ESP WiFi 모듈로 TCP 클라이언트 구현 |
| Raspberry Pi | 관리실 | 멀티스레드 TCP 서버(`iot_server`) — pthread 기반으로 클라이언트마다 스레드를 붙여 아두이노·DB클라이언트·블루투스클라이언트를 동시 수용. 클라이언트 이름 태그를 매칭해 메시지를 특정 클라이언트로 라우팅 |
| Raspberry Pi (DB 클라이언트) | 관리실 | `iot_client_sensor_device` — 서버로부터 전달받은 메시지를 분석해 MySQL에 INSERT/UPDATE/SELECT 수행 |
| Raspberry Pi (BT 중계 클라이언트) | 관리실 | `iot_client_bluetooth` — 서버와 STM32 사이를 중계하는 별도 프로그램. STM32 요청 시 자체 MySQL 커넥션으로 DB를 조회하고 결과를 Bluetooth로 응답 |
| STM32 | 관리실 | 표시부 — UART로 블루투스 모듈과 연결해 응답 수신, I2C LCD에 슬롯별 상태 실시간 표시 |

### 통신 구간
| 구간 | 방식 |
|---|---|
| Arduino ↔ Raspberry Pi | Wi-Fi (TCP Socket) |
| Raspberry Pi (서버) ↔ Raspberry Pi (BT 클라이언트) | 로컬 TCP |
| Raspberry Pi (BT 클라이언트) ↔ STM32 | Bluetooth |
| STM32 ↔ LCD | I2C |

### 하드웨어 구성 (3슬롯 기준)
RFID 리더(MFRC522) 1, RFID 카드 3, 서보모터(SG90) 3, IR 센서 3, 수위 센서 3, DC 모터(팬) 3, 부저 1, LCD(I2C) 1

## 동작 시나리오
1. **우산 보관**: 빈 슬롯에 RFID 태그 → 서보 열림 → 우산 삽입(IR 감지) → 서보 잠금 → DB에 슬롯번호+UID+시간 기록 → 수위센서로 젖은 정도 측정 후 DC모터(팬) 가동
2. **우산 회수(본인)**: 본인 카드 태그 → 저장된 UID와 태그된 UID 비교, 일치할 때만 슬롯을 비우는 인증 로직 → 서보 열림 → 우산 인출(IR 감지) → DB 업데이트(회수 완료)
3. **도난 시도**: 타인 카드 태그 → UID 불일치 → 서보 잠김 유지 / 강제 인출 시도 → 잠금 상태에서 IR이 "우산 없음"을 감지 → 도난 판정 → 부저 경고 + LED 적색 점등 → DB에 도난 로그 저장
4. **건조 모니터링**: 수위센서 값을 3단계(HIGH/MID/LOW) 임계값으로 구분해 DC모터 속도 제어 → LCD에 슬롯별 건조 상태 표시 → 건조 완료 시 자동 정지

## 통신 프로토콜
`[대상ID]액션@파라미터` 형식으로 통일해, TCP·Bluetooth 어느 경로로 들어와도 서버가 동일한 파서(`strtok` 기준 `[ @ ]`)로 처리하도록 설계.
- 데이터 메시지 예: `[UMB_DB]STORE@1@07FCEB05@0`, `[UMB_DB]THEFT@1`
- 로그인 메시지는 별도 포맷: `[UMB_ARD:PASSWD]` (콜론 포함, 클라이언트 인증용)

## 트러블슈팅 요약
| 문제 | 원인 | 해결 |
|---|---|---|
| 서보 동작 중 RFID 인식 불안정 | `delay(1000)`으로 서보 이동 중 CPU 블로킹 → RFID 폴링 중단 | `millis()` 기반 non-blocking 전환, 700ms 후 자동 detach |
| 이벤트 발생 전까지 서버 연결 안 됨 | TCP 연결 로직이 이벤트 발생 시점에만 실행됨 | Wi-Fi 연결 직후 별도 `connectTcpServer()` 호출로 분리 |
| 클라이언트 ID 길이로 서버 버퍼 오버플로우 | ID 12자가 서버 `ID_SIZE=10` 버퍼 초과 | ID를 `UMB_ARD`(7자)로 축소 |
| 개행문자 차이로 UID 매칭 실패 | `client.println()`이 붙이는 `\r`이 서버 파싱값에 남음 | `client.print()` + `\n`만 전송하도록 통일 |
| 멀티스레드 공유 자원 레이스 컨디션 | BT 클라이언트에서 DB 커넥션·BT 소켓을 여러 스레드가 동시 공유 | 자원별 뮤텍스 분리(`g_db_mutex`, `g_bt_mutex`) |
| 수위센서 값 흔들림으로 건조 상태 채터링 | 임계값 근처에서 아날로그 값이 미세하게 흔들림 | 진입/해제 임계값을 다르게 둔 히스테리시스 3단계 도입 |

## 결과
- 아두이노-라즈베리파이-STM32 3개 보드가 TCP·Bluetooth 경로로 정상 통신하며, 슬롯 상태가 DB에 실시간 반영됨을 확인
- 두 스레드가 DB·Bluetooth 소켓을 동시에 사용해도 뮤텍스로 충돌 없이 안정 응답하는 것을 반복 테스트로 확인
- 워터센서 값이 흔들리는 구간에서도 슬롯 상태가 안정적으로 유지됨을 확인
- 관리자 원격 개방(`[YGY_ADM]SLOT@1@OPEN`) 기능 검증 완료
- 웹페이지(userTable.php / slotTable.php / logTable.php)에서 등록 사용자, 슬롯 상태, 이벤트 로그가 실시간 조회됨을 확인

## 고찰
- 여러 스레드가 하나의 DB 커넥션·소켓을 공유할 때 발생할 수 있는 레이스 컨디션을 직접 겪으며, 공유 자원을 어떤 단위로 잠가야 하는지(뮤텍스 분리 설계) 이해함
- 센서 노이즈는 소프트웨어로 없앨 수 없고, 히스테리시스처럼 상태 전이 자체를 설계로 흡수해야 한다는 점을 체감함
- TCP와 Bluetooth라는 이기종 통신 경로를 하나의 메시지 규격으로 통합해 라우팅하는 프로토콜 설계 경험을 쌓음
- 멀티스레드 서버에서 클라이언트 인증·라우팅·DB 트랜잭션을 계층적으로 설계하는 경험을 함

## 참고
- 원본 노션 문서에 `userTable.php` / `slotTable.php` / `logTable.php` / `index.html`(웹 조회 페이지)의 실제 구현부는 첨부되어 있지 않아 이 저장소에는 포함되어 있지 않다.
- STM32 `clcd.h`/`clcd.c`(I2C LCD 헬퍼)도 시그니처만 알려져 있어 실제 구현은 포함되어 있지 않다. 팀에서 쓰던 실제 파일을 추가하면 빌드 가능하다.
